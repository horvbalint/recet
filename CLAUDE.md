# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Recet is a recipe manager for households: a **client-only Nuxt 4 SPA** (`ssr: false`) that talks straight to a **SurrealDB v3** instance over WebSocket. There is no Nitro server layer and no API of our own in this repo — the browser opens one authenticated `Surreal` connection and every read/write is a SurrealQL query sent from the client.

That makes [db.surql](db.surql) the actual backend: table permissions, record-level auth, events, `fn::` functions and `DEFINE API` endpoints all live there. **Any change to what data a user may see or write is a change to `db.surql`, not to Vue code** — the frontend cannot be trusted to enforce it and doesn't try.

Recet also consumes [nebula](https://github.com/horvbalint/nebula) as a Nuxt layer (`extends: ['nebula']`) for all UI primitives. [node_modules/nebula/CLAUDE.md](node_modules/nebula/CLAUDE.md) documents its components, tokens and conventions, and **its usage and style rules apply here too** — read it before writing UI code.

## Commands

```bash
pnpm install
pnpm dev              # :3000 — expects SurrealDB at ws://localhost:8000
pnpm build            # nuxt build
pnpm lint             # not a script — run `npx eslint .` (add --fix)
pnpm generate-types   # surreal-ts type generation — CURRENTLY BROKEN, see below
```

There is **no test suite and no type-check script**; `vue-tsc` is installed but not wired up. ESLint (`@antfu/eslint-config` with `formatters.css`) is the formatter for TS, Vue *and* CSS — no Prettier. VS Code is configured to fix on save.

### Database setup / schema changes

`db.surql` is a single idempotent `BEGIN TRANSACTION … COMMIT` script using `DEFINE … OVERWRITE` everywhere, so it is **re-run in full** after every edit rather than diffed. It hard-fails unless `$pluginsBucketPath` and `$recipeImagesBucketPath` params are defined first; `$allowedSignupEmails` gates signup (defaults to `[]` = nobody), and the three `$openAi*` params enable recipe import.

Data reshaping that `OVERWRITE` can't do goes in [migrations/](migrations/) as a dated one-off `.surql` file, applied by hand.

[app/db.ts](app/db.ts) holds the `In*`/`Out*` types and is eslint-ignored. It was generated by `pnpm generate-types` (surreal-ts, reading the *live* database rather than `db.surql`), but **that command is currently broken — after changing a table or field definition, edit `app/db.ts` by hand** to match, following the existing `In*`/`Out*` shape.

### The SurrealDB plugin (`surreal-plugin/`)

A Rust `cdylib` compiled to wasm32-wasip2 via [surrealism](https://crates.io/crates/surrealism), loaded as `DEFINE MODULE mod::recet`. Two `#[surrealism]` functions run *inside* the database:

- `process_image` ([image.rs](surreal-plugin/src/image.rs)) — resize to 600px, JPEG-encode, compute blurhash. Called by `fn::add_image_to_recipe`.
- `scrape_for_recipe` ([recipe_scraper.rs](surreal-plugin/src/recipe_scraper.rs)) — fetch a URL (or take raw text), flatten to text, send to an OpenAI-compatible API, then resolve the returned ingredient/unit/cuisine/tag/meal names to existing records via fulltext `@@` lookup scoped to the household. Called by `DEFINE API "/recipe/scrape/:type"`. **Recipe import from a URL is currently broken**: the current SurrealDB version requires the allowed hosts to be baked into the plugin's capabilities at build time, so the plugin can no longer `http::get` an arbitrary user-supplied site.

Build with `./surreal-plugin/build.sh` (`surreal module build --out ./recet.surli .`) and copy `recet.surli` into the DB's `plugins` bucket directory. Network/`http::*` capabilities are granted in [surrealism.toml](surreal-plugin/surrealism.toml).

## Architecture

### Connection and auth bootstrap

Three route middlewares run in a fixed order, wired per-route in `nuxt.config.ts` `routeRules` (which also picks the layout):

1. [db.global.ts](app/middleware/db.global.ts) — global: connects the singleton `db` ([composables/db.ts](app/composables/db.ts)) with reconnect, `USE NS recet DB recet`. Everything else assumes this ran.
2. [auth.ts](app/middleware/auth.ts) — re-authenticates from the refresh tokens in `localStorage['recet_tokens']` (kept in sync by `db.subscribe('auth', …)`), fills `authUser` and `authMemberships`, else redirects to `/auth/login?to=…`.
3. [household.ts](app/middleware/household.ts) — loads the user's households, restores `localStorage['currentHousehold']` (or falls back to the first / `/create-first-household`) and calls `switchHousehold`, which also switches the i18n locale and dayjs locale.

`/auth/**` and `/create-first-household` opt out of parts of this; `/public/recipe/*` instead runs [guest-auth.ts](app/middleware/guest-auth.ts), which signs in through the `recipe_guest` record access — a 5-minute session whose `$auth` *is the recipe record*.

Auth state is module-level `ref`s in [composables/auth.ts](app/composables/auth.ts) (not `useState`), so it is shared process-wide. Signup/signin pick the `desktop_user` or `mobile_user` access based on viewport — the two are identical today.

### The household is the tenancy boundary

Almost every table is created through `fn::define_household_table(name)`, which gives it a `household` field plus `created_at`/`updated_at` and the standard permission set: read if `fn::can_read_household(household)` or `fn::has_guest_access(id)`, write if `fn::can_write_household(household)`. Roles come from the `member` relation (`owner` / `writer` / `guest`).

Consequences to keep in mind when writing queries or components:

- **Every write must set `household: currentHousehold.value!.id`.** Cross-household references are rejected by field `ASSERT`s (`ASSERT household = $value.household`), not merely unenforced.
- Reads generally don't need an explicit household filter (permissions handle it), but list queries add `WHERE household = …` anyway for index use — follow the surrounding code.
- The client-side role computeds `isCurrHouseholdOwner` / `isCurrHouseholdEditor` / `isCurrHouseholdViewer` only hide UI; the DB is what actually enforces the rule.
- `fn::has_guest_access` is how a public recipe page also reads its author/tags/cuisine/meals/ingredients under the guest session.

### Querying conventions

Always use the tagged template `surql` (re-exported from `composables/db.ts`) and `.collect<[T, …]>()` — the tuple type parameter maps positionally to the statements in the query:

```ts
const [meals, tags] = await db
  .query(surql`SELECT * FROM meal; SELECT * FROM recipe_tag;`)
  .collect<[OutMeal[], OutRecipeTag[]]>()
```

Types come from [app/db.ts](app/db.ts) as `In*`/`Out*` pairs (`In` = what you write, ids optional and relations as `RecordId`; `Out` = what you read back, relations fetched into objects).

Composed/conditional queries use `query.append(surql\`…\`)` and the expression builders imported from `surrealdb` (`and`, `or`, `eq`, `not`, `containsAll`, `containsAny`, `inside`, `matches`, `raw`) — see `constructWhereConditions` in [composables/recipe.ts](app/composables/recipe.ts), which is deliberately shared between the recipe list filter and meal-rule-driven meal-plan generation so both interpret a `MealRuleConditions` object identically.

Server-side calls that aren't plain CRUD go through `fn::…` or `api::invoke("/path", …)` inside a query — e.g. `fn::add_recipe_to_shopping_list`, `fn::add_image_to_recipe`, `api::invoke("/invitation/accept", …)`.

Fulltext search picks the index by household language: `WITH INDEX hungarian_search_name` vs `english_search_name` (`snowball` analyzers defined per language).

### State: module-level refs, not stores

There is no Pinia. Cross-page state is module-scope `ref`s + `useAsyncData` handles created at module load (`householdQuery`, the recipe list state in `useRecipeState`). Note the comment in [composables/households.ts](app/composables/households.ts): the `useAsyncData` factory must **not** be `async` at module level.

The recipe list is an append-only infinite scroll — `pageIndex` drives `useAsyncData`'s `watch`, results are pushed onto a `recipes` array, and `clearRecipeCache()` resets the array *and* deletes `recipe-card-*` keys out of `useNuxtApp().payload.data`. `firstPageQueriedAt` is pinned into the `WHERE` so newly created recipes don't shift pagination mid-scroll.

### Images

Recipe images live in the `recipe_images` bucket with per-action permissions checked against the owning recipe. The file key is the recipe's record id, so a recipe has at most one image. The client sends an `ArrayBuffer` to `fn::add_image_to_recipe` (which delegates resizing + blurhash to the wasm plugin) and reads back through `fn::get_recipe_image`, caching object URLs in a module-level `Map` in [composables/recipe.ts](app/composables/recipe.ts). `image_blur_hash` on the recipe row is what the card renders while loading.

### View transitions

Cross-document-style transitions are driven manually: `startTransitionThen(fn)` in [composables/utils.ts](app/composables/utils.ts) stores the transition's `resolve`, and the `page:finish` hook in [plugins/view-transition.ts](app/plugins/view-transition.ts) calls `resolvePendingViewTransition()`. Recipe card → recipe page continuity works by stashing the clicked recipe (`setCachedRecipe`) so the detail page can render instantly and share `view-transition-name`s. Names/animations live in [assets/view-transitions.css](app/assets/view-transitions.css).

### Master data CRUD pattern

The master-data entities (cuisine, meal, ingredient, ingredient_category, unit, shop, recipe_tag, meal_rule) are each just a `<x>/master-data/page.vue` + `modal.vue` pair delegating to the generic [master-data/layout.vue](app/components/master-data/layout.vue) (table + create/edit/delete wiring, `neb-table` columns, confirm + toast) and [master-data/modal.vue](app/components/master-data/modal.vue) (generic `CREATE ONLY type::table($table)` / `UPDATE ONLY … MERGE`, injecting `household`). **Adding a new master-data entity means adding the table in `db.surql` and a page/modal pair — not new CRUD code.** `transformBeforeCreate` / `transformBeforeEdit` are the escape hatches for entity-specific shaping.

Components are auto-imported with the default Nuxt path prefixing, so `components/cuisine/master-data/modal.vue` is `<cuisine-master-data-modal>`.

### i18n

`@nuxtjs/i18n`, `strategy: 'no_prefix'`, locales `en` and `hu` in [i18n/locales/](i18n/locales/). The active locale follows the **household's** `language` field, not the browser, once a household is selected. **Add every new key to both `en.json` and `hu.json`** — a missing key silently falls back at runtime. Nebula's own strings live under `nebula.*` in the layer's locale files.

## Conventions

- Only write comments when something is used in a way, that an unsuspecting editor might change it without knowin the consequences. Don't annotate everything with comments if it is easily deductable from the codeblock below.
- Reach for nebula's components and composables (`neb-*`, `useNebToast`, `useNebConfirm`, `useAppBreakpoints`, `neb-state-content`) before hand-rolling — check the layer first.
- Vue SFCs: blank line between sibling tags; keep a tag on one line until it has ~4 attributes; single-line `useNebToast({ … })` calls unless they carry action functions; write event handlers as `@click="handler()"`, not `@click="handler"`.
- If instructions are unclear or can't be followed, ask rather than assume.

Styling: recet predates nebula's `--neb-*` semantic tokens and uses the raw scales (`--neutral-color-600`, `--primary-color-500`) plus explicit `.dark-mode { … }` blocks at the bottom of `<style scoped>` — match that in existing files. Spacing/sizing tokens (`--space-*`, `--text-*`, `--radius-*`, `--duration-*`) and custom media (`@media (--tablet-viewport)`) come from the layer.
